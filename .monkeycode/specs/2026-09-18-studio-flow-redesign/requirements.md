# 主台流程重设计（纵向阶段卡片流）— 需求文档

- 特性编号：2026-09-18-studio-flow-redesign
- 状态：待评审
- 关联文档：`2026-09-18-skill-pipeline`（流水线单一数据源）

## 1. 背景

主台（Studio）是逐章协作的核心界面。当前主台把「写作流水线」拆散在三处：

- 顶部进度条（`PIPELINE` 数组）
- 左侧资产编辑区（`TABS` 手写 tab）
- 右侧副栏（`sideKind` 审稿/侧写）

三者各自维护一份阶段/字段映射，导致以下问题（调研证据见设计文档附录）：

- P0-1：`suggest`（卡壳建议）target 与 `review`（章节审稿）相同，前端把建议写进「审稿」字段，后端却跳过落盘，建议顶掉正式审稿。
- P0-2：`chapter-prose` 说明书要求续写，流水线却固定 `replace` 覆盖整章。
- P0-3：拆书线 `td-imitate` / `td-craft` 共用 `target: "td-craft"`，阶段归属先到先得，仿写骨架与提炼技法互相串台。
- P1/P2：`kickoff.md` 描述漏「道具」阶段、Skill frontmatter `order` 与流水线不一致、左栏 tab 顺序与流水线不一致、`quick`/`STEPS` 死代码、`skills.js` 写死写作类清单、`continue` 缺 `artifact`、拆书台字段映射未收敛。

用户已裁定：本次范围 = **修完上述对不上问题 + 把主台重排为「纵向阶段卡片流」**；正文边界 = **chapter-prose 写整章 / continue 续写**。

## 2. 术语

- **阶段（Stage）**：流水线中的一个环节，唯一定义于 `shared/pipeline.json`，含 `id/label/target/builtin/artifact/...`。
- **阶段卡片（Stage Card）**：主台纵向流中一张卡，对应一个阶段。
- **关联（Refs/Deps）**：阶段卡片上展示的前置依赖与本阶段产出的资产、人物、道具、伏笔。
- **写作线 / 拆书线**：`pipeline.json` 的 `lines`，主台按台过滤显示。
- **整章 / 续写**：`chapter-prose` 产出完整一章（replace）；`continue` 只续写后半段（append 到章尾）。

## 3. 需求

### 3.1 主台呈现为纵向阶段卡片流

**R1** 当用户进入主台时，系统应把当前台（写作线 / 拆书线）的所有阶段按 `pipeline.json` 顺序渲染为纵向排列的阶段卡片，每张卡展示：阶段名、状态、产出摘要、依赖、操作按钮。

**R2** 当用户切换台（写作线 / 拆书线）时，系统应只渲染该台的阶段卡片，且阶段顺序与 `pipeline.json` 的 `index` 一致。

**R3** 当阶段属于写作线且已产出资产时，系统应在卡片内展示该资产的摘要（truncate 到一屏可读）与「查看/编辑」入口。

### 3.2 阶段状态与进度

**R4** 每个阶段卡片应处于以下状态之一：`未开始 / 进行中 / 已完成 / 失败 / 已跳过`，且状态由阶段产出字段与任务状态共同推导。

**R5** 当某阶段正在生成时，系统应在对应卡片内显示进度（已用时长 / 预计时长 / 字数），并在完成或失败后更新卡片状态。

**R6** 当用户处于自动开书流水线时，系统应逐卡点亮「进行中」→「已完成」，并在首屏可见范围内自动滚动到当前阶段卡片。

### 3.3 阶段操作

**R7** 每个阶段卡片应提供：生成/重跑、跳过、查看产出、编辑产出（若可编辑）四类操作。

**R8** 当用户点击「重跑」时，系统应仅重跑该阶段，且不改变其他阶段已完成状态。

**R9** 当用户点击「跳过」时，系统应把该阶段标记为 `已跳过` 并推进到下一阶段。

### 3.4 关联管理

**R10** 当阶段产出涉及人物 / 道具 / 伏笔时，系统应在对应卡片上展示这些关联条目，并支持跳转到该条目的编辑位置。

**R11** 当用户在阶段卡片上查看依赖时，系统应展示该阶段所依赖的前置阶段（如正文依赖细纲、细纲依赖大纲）并标明依赖是否已满足。

### 3.5 修正流水线与 Skill 的一致性（P0–P2）

**R12** 当 `suggest` 阶段产出时，系统应把建议写入独立的「卡壳建议」字段，禁止覆盖 `review`（章节审稿）字段，且审稿结论只由 `review` 阶段产生。

**R13** 当 `chapter-prose` 阶段产出时，系统应用生成结果替换该章正文（整章）；当 `continue` 阶段产出时，系统应把结果追加到该章正文结尾（续写）。

**R14** 拆书线的每个阶段应拥有唯一 `target`，`td-imitate`（仿写骨架）与 `td-craft`（提炼技法）应落到各自独立字段，不得互相覆盖。

**R15** `kickoff.md` 等内置 Skill 说明书描述的自动阶段序列应与 `pipeline.json` 一致（含「道具」阶段）。

**R16** 内置 Skill frontmatter 的 `order` 应与 `pipeline.json` 中同阶段顺序一致。

**R17** 主台左栏 tab 顺序、拆书台 tab/字段映射、写作类 Skill 判定、`continue` 的 `artifact` 应全部从 `pipeline.json` 派生，删除界面不再使用的 `quick`/`STEPS` 死代码。

### 3.6 兼容与数据

**R18** 系统应保持既有 Skill `id` 不变，并在升级后仍能读取旧小说数据（缺少新增字段时按空值处理，不报错）。

**R19** 当一次生成只产出部分内容时，系统应保留已有资产，仅在字段级做 upsert/append，不得整本覆盖。

## 4. 非目标

- 不改变模型调用协议、不改变既有 Skill 的创作要求。
- 不引入新的数据存储后端；仍为本地 JSON。
- 不重做拆书线的分析算法，仅收敛其字段/阶段映射。

## 5. 验收标准

- AC1：写作线与拆书线阶段卡片顺序与 `pipeline.json` 完全一致。
- AC2：`suggest` 产出后 `chapter.reviewReport` 不变，建议落在独立字段。
- AC3：`chapter-prose` 重跑后该章正文被整章替换；`continue` 重跑后正文长度增加且旧内容保留。
- AC4：`td-imitate` 与 `td-craft` 产出分别落在不同字段，互不覆盖。
- AC5：`pipeline-test`、`spark-deck-test`、`llm-mock-test`、`tsc --noEmit`、`vite build` 全绿；接口冒烟通过。
- AC6：`grep` 确认界面代码不再引用手写 `TABS`/`TEAR_TABS`/`TAB_FIELDS`/`STEPS` 作为阶段来源。
